# CuTe GEMM 四个教程版本的优化演进

> 对应官方示例：`sgemm_1.cu`、`sgemm_2.cu`、`sgemm_sm70.cu`、
> `sgemm_sm80.cu`
>
> 整理日期：2026-09-23

这四个版本并不是简单地“后一份代码全面替代前一份”，而是在同一 GEMM 数据流
上逐步加入：

```text
线程分区抽象
→ 向量化 Copy 与 register staging
→ shared/register 双层流水
→ cp.async、多级 shared pipeline 与 Tensor Core
```

## 1. 总览

| 版本 | Copy | Compute | Pipeline | 主要目的 |
|---|---|---|---|---|
| `sgemm_1` | 普通 `copy`，global→shared | `UniversalFMA` | 基本串行 | 解释 CTA、copy 和 math partition |
| `sgemm_2` | `TiledCopy`，global→register→shared | `TiledMMA<UniversalFMA>` | 预取下一 K tile | 显式描述 Copy/MMA 分区并隐藏部分 global-load 延迟 |
| `sgemm_sm70` | 与 `sgemm_2` 类似 | register fragment 上的 `UniversalFMA` | shared 与 register 双层流水 | 进一步隐藏 shared→register 延迟 |
| `sgemm_sm80` | `cp.async` global→multistage shared | SM80 Tensor Core MMA | 多级 shared/register pipeline | 使用异步 Copy 与 Tensor Core 提升吞吐 |

四个版本不变的逻辑框架：

```text
完整 Tensor
  → CTA tile
  → Copy partition
  → shared-memory tile
  → Math/MMA partition
  → register accumulator
  → epilogue
```

## 2. `sgemm_1`：建立正确的数据流

### 数据路径

```text
global A/B
   ↓ 普通 copy
shared A/B
   ↓ UniversalFMA
register C accumulator
   ↓ axpby
global C
```

### 核心配置

```text
CTA tile：128×128×8
Block：256 threads
Copy Thread Layout：32×8
Compute Thread Layout：16×16
```

### 每线程任务

Copy：

```text
A/B tile：128×8
线程布局：32×8
每线程：4×1 values
```

Compute：

```text
C tile：128×128
线程布局：16×16
每线程：8×8 C accumulators
```

### Mainloop

```text
global→shared
barrier
GEMM
barrier
下一 K tile
```

### 特点

- 结构最直观；
- copy 与 compute 基本串行；
- 没有显式预取；
- 没有使用 Tensor Core；
- `cp_async_fence/wait` 在当前实例中没有异步事务可等待，只是官方保留的潜在位置。

## 3. `sgemm_2` 相比 `sgemm_1`

### 优化一：用 `TiledCopy` 代替手工 Copy Thread Layout

`sgemm_1`：

```cpp
local_partition(gA, tA, threadIdx.x);
local_partition(sA, tA, threadIdx.x);
```

`sgemm_2`：

```cpp
auto thr_copy = copy_a.get_slice(threadIdx.x);
auto src = thr_copy.partition_S(gA);
auto dst = thr_copy.partition_D(sA);
```

收益：

- Copy Atom、Thread Layout、Value Layout 绑定在同一个对象中；
- source/destination 可以使用不同 TV Layout；
- 指令宽度和分区兼容性可以在编译期检查；
- 后续更容易替换成 `cp.async`、`ldmatrix` 等硬件 Copy Atom。

### 优化二：NT 路径使用 128-bit vector load

NT：

```text
A 的 M mode 连续
B 的 N mode 连续
```

所以每线程的 `4×1 float` 可以组合为：

```text
4 × 32 bit = 128 bit
```

使用：

```cpp
Copy_Atom<UniversalCopy<uint128_t>, float>
```

TN 当前配置仍使用标量 Copy，因为连续 K 坐标被分配给不同线程；同一线程沿
M/N 重复负责的元素相隔 `ldA/ldB`。

### 优化三：global→register→shared staging

新增：

```text
tArA/tBrB：下一 K tile 的 register staging
```

数据路径：

```text
global next tile → register
shared current tile → GEMM
下一轮 register → shared
```

重要前提：

```text
当前 GEMM 不读取 tArA/tBrB
```

因此当前 GEMM 与下一 tile 的普通 global load 没有数据依赖，为延迟重叠创造
机会。若下一条指令立即读取 staging register，scoreboard 会等待 load 完成，
无法隐藏延迟。

### 优化四：用 `TiledMMA` 代替手工 `tC`

```cpp
make_tiled_mma(
    UniversalFMA<float,float,float>{},
    Layout<Shape<_16,_16,_1>>{});
```

当前仍是 `1×1×1` 标量 FFMA，但：

- MMA Atom 与线程分区绑定；
- `partition_A/B/C` 自动生成对应 view；
- fragment 第一维显式成为 `MMA` mode；
- 后续可替换成硬件 MMA Atom。

### 当前性能效果

A100 MIG、FP32 NT、`M=N=K=512`：

```text
sgemm_1：1165.0 GFLOP/s
sgemm_2：1298.9 GFLOP/s
```

相对提升：

```text
约 11.5%
```

该提升是向量化 Copy、register staging、shared Layout 等多项变化的综合结果，
不能全部归因于单一优化。

## 4. `sgemm_sm70` 相比 `sgemm_2`

### `sgemm_2` 的不足

`sgemm_2` 的 GEMM 直接读取 shared-memory view：

```cpp
gemm(mma, tCsA, tCsB, tCrC);
```

global load 已经做了一轮预取，但 shared→register 的 operand load 尚未显式
流水化。

### 优化一：显式 A/B register fragment

新增：

```cpp
Tensor tCrA = thr_mma.make_fragment_A(tCsA);
Tensor tCrB = thr_mma.make_fragment_B(tCsB);
```

数据路径：

```text
global
  → copy staging register tArA/tBrB
  → shared sA/sB
  → MMA operand register tCrA/tCrB
  → FFMA
  → accumulator tCrC
```

### 优化二：K tile 内再拆 `k_block`

```cpp
for (k_tile)
  for (k_block)
```

在计算当前 register block 时：

```text
shared → register：准备下一个 k_block
global → register：准备下一个 K tile
register GEMM：计算当前 k_block
```

### 优化三：prologue 与稳态分离

第一次 shared 填充前没有旧 tile 需要保护，因此只需要 copy 后的 barrier。

后续重用 shared memory 时：

```text
copy 前 barrier：确保旧 tile 已经读完
copy 后 barrier：确保新 tile 已经写完
```

### 代价

- 更多 A/B register fragment；
- 寄存器压力上升；
- occupancy 可能下降；
- 可能发生 local-memory spill；
- 双层循环和同步更加复杂。

### 当前性能效果

相同 A100 MIG、FP32 NT、`512³`：

```text
sgemm_2：    1298.9 GFLOP/s
sgemm_sm70：1319.5 GFLOP/s
```

相对提升：

```text
约 1.6%
```

当前编译结果约使用 `102～106 registers/thread`，`LOCAL:0`，没有 spill。

该示例名称虽然包含 SM70，但仍使用 `UniversalFMA<float>`，没有使用 Volta
Tensor Core。SM70 指的是流水线组织适用于 Volta 及更新架构。

## 5. `sgemm_sm80` 相比 `sgemm_sm70`

### 优化一：`cp.async` 直接 global→shared

```cpp
Copy_Atom<
    SM80_CP_ASYNC_CACHEALWAYS<uint128_t>,
    half_t>
```

数据路径从：

```text
global → ordinary register staging → shared
```

变为：

```text
global --cp.async--> shared
```

并通过：

```cpp
cp_async_fence();
cp_async_wait<N>();
```

维护异步 transaction group。

### 优化二：多级 shared-memory pipeline

Shared Tensor 增加 PIPE mode：

```text
sA: (BLK_M,BLK_K,PIPE)
sB: (BLK_N,BLK_K,PIPE)
```

当前示例：

```text
PIPE = 3
```

可以同时存在：

```text
stage 0：正在计算
stage 1：已经加载完成
stage 2：正在从 global 异步加载
```

### 优化三：Swizzled shared Layout

Swizzle 同时服务于：

- 128-bit global→shared Copy；
- shared-memory bank-conflict 避免；
- `ldmatrix` shared→register load；
- Tensor Core fragment 布局。

### 优化四：Tensor Core MMA

```cpp
SM80_16x8x16_F16F16F16F16_TN
```

相比前三个版本的标量 `FFMA`：

```text
前三个版本：CUDA Core FFMA
SM80 版本： Tensor Core HMMA
```

### 优化五：Copy 与 Compute 双重流水

同一时刻可进行：

```text
K tile k+1：global → shared
K tile k：  shared → register
K block：   register Tensor Core compute
```

### 当前性能效果

A100 MIG、FP16 TN、`512³`：

```text
sgemm_sm70： 1319.5 GFLOP/s
sgemm_sm80：11632.7 GFLOP/s
```

数值上约为 `8.82×`。

但这不是公平的单变量比较：

```text
sgemm_sm70：FP32 NT，普通 FFMA
sgemm_sm80：FP16 TN，Tensor Core
```

差异同时来自数据类型、MMA 指令、Copy、pipeline 和 Layout，不能把 `8.82×`
全部归因于 `cp.async`。

## 6. 测试结果

测试环境：

```text
GPU：A100-SXM4-80GB MIG 1g.20gb，14 SMs
CUDA：12.2
CUTLASS commit：147295a3
Shape：M=N=K=512
```

| 版本 | 数据类型/路径 | 最大绝对误差 | 性能 | 相比上一版本 |
|---|---|---:|---:|---:|
| `sgemm_1` | FP32 NT | `2.88766e-05` | `1165.0 GFLOP/s` | 基线 |
| `sgemm_2` | FP32 NT | `2.88766e-05` | `1298.9 GFLOP/s` | `+11.5%` |
| `sgemm_sm70` | FP32 NT | `2.88766e-05` | `1319.5 GFLOP/s` | `+1.6%` |
| `sgemm_sm80` | FP16 TN Tensor Core | `0.089232` | `11632.7 GFLOP/s` | 非同类型比较 |

四个版本均通过 CPU reference：

```text
RESULT_CHECK: PASS
```

## 7. 最简记忆

```text
sgemm_1：
  先把 GEMM 做正确

sgemm_2：
  Copy/MMA 对象化
  向量化 global load
  register 预取下一 tile

sgemm_sm70：
  shared→register 也做流水
  计算当前 block 时准备下一个 block

sgemm_sm80：
  cp.async 多级 shared pipeline
  swizzle + ldmatrix
  Tensor Core
```

## 8. 阅读建议

阅读每个版本时只问四个问题：

1. 当前、下一 K tile 分别存在哪里？
2. global→shared 使用什么 Copy Atom？
3. shared→register 是否提前加载？
4. compute 使用 FFMA 还是 Tensor Core MMA？

只要能画出每个版本的存储时序，就不需要死记完整 mainloop。
